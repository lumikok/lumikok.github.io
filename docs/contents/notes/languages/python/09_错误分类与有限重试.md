# 错误分类与有限重试

## 先分类，再决定是否重试

重试是在一次调用失败后重新调用，不是捕获所有异常后无限循环。先判断错误是否可能暂时恢复，再判断重复操作是否安全。

| 失败类型 | 本例处理 | 理由 |
| --- | --- | --- |
| 输入校验失败，如 `ValueError` | 直接传播 | 原样重复输入通常不能修正数据 |
| HTTP 400、401 | 立即停止 | 应修正请求或凭证，而不是原样重发 |
| HTTP 429、500、503 | 允许有限重试 | 在本例中作为可能恢复的失败处理，不保证重试成功 |
| 直接抛出的 `TimeoutError` | 安全前提下有限重试 | 没及时收到结果，但服务端执行结果可能未知 |
| 响应结构或内容校验失败 | 不由本例自动重试 | 传输成功不代表数据合格，应单独制定处理策略 |

这些是本例的策略，不是所有接口的统一规则。模型请求重试可能增加费用，也可能返回不同回答；创建订单等有副作用的调用，必须先考虑查询或幂等保障。超时不能证明服务端没有执行，详见[超时与执行结果未知](./08_HTTP请求与JSON数据转换.md#超时与执行结果未知)。

## 尝试次数与停止条件

`max_attempts` 表示总尝试次数，包含首次调用：

```text
max_attempts = 3
第1次调用 → 失败 → 等待 → 第2次调用 → 失败 → 等待 → 第3次调用
```

最多调用 3 次、重试 2 次、等待 2 次，不是首次调用后再重试 3 次。

- 成功：立即返回提供者结果，不继续调用；
- 不可重试错误：无论出现在第几次，都立即向上传播；
- 可重试错误：未到上限才等待并再次调用；
- 最后一次失败：继续抛出当前异常，不再等待、不返回假成功；
- `max_attempts < 1`：调用前拒绝。否则循环可能一次都不执行，函数静默返回 `None`。

## 最小重试实现

以下根据受控重试实验 `retry_demo.py` 提炼，保留控制流程，去掉与具体消息和密钥有关的参数。假定 `max_attempts` 为整数、`base_delay` 为非负数；这是同步、阻塞式示例。

```python
import time
from urllib.error import HTTPError


def call_with_retry(provider, max_attempts=3, base_delay=0.1):
    if max_attempts < 1:
        raise ValueError("max_attempts 必须至少为 1")

    for attempt in range(1, max_attempts + 1):
        print(f"尝试 {attempt}/{max_attempts}")
        try:
            return provider()
        except HTTPError as error:
            print(f"失败：HTTP {error.code}")
            if error.code not in (429, 500, 503):
                raise
            if attempt == max_attempts:
                raise
        except TimeoutError:
            print("失败：TimeoutError")
            if attempt == max_attempts:
                raise

        delay = base_delay * 2 ** (attempt - 1)
        print(f"等待 {delay:g} 秒")
        time.sleep(delay)
```

关键写法：

- `provider` 是函数对象，`provider()` 才执行调用。可以传入模拟提供者，或封装好参数的真实调用函数；
- `return provider()` 成功时原样返回结果；未匹配的异常自动传播，不必写一个捕获所有错误的分支；
- `HTTPError.code` 是 HTTP 状态码；它与本地数据校验抛出的 `ValueError` 属于不同失败层次；
- 裸 `raise` 重新抛出正在处理的异常。这里应在 `except` 内判断上限，不能放到循环结束后的 `else` 中，指望它记住上一次失败；没有正在处理的异常时，裸 `raise` 会导致 `RuntimeError`；
- 等待语句只有在“可重试且未到上限”的路径才会到达，所以最后失败不会多等一次。

基础异常传递见[异常](./05_异常.md)。本实现只捕获直接抛出的 `TimeoutError`，不覆盖可能包装在 `URLError.reason` 中的超时，也不是完整网络错误分类器。

## 等待时间与日志

第 `attempt` 次失败后、下一次调用前的等待为：

```text
delay = base_delay × 2^(attempt − 1)
```

例如 `base_delay=0.1`、总尝试上限为 3，两次等待分别是 0.1、0.2 秒。总耗时还包含每次调用自身的耗时，不能把等待总和当作整个业务的超时上限。

日志至少区分尝试序号、失败类型或状态码、安排的等待时间。不要打印密钥等敏感数据；日志也不能代替次数和结果断言。

## 用受控失败序列验证

预设每次调用的结果，才能稳定检查控制流程。例如 `503 → 400 → 成功` 应在第二次停止，而不是为了等到成功继续第三次。

下表中的状态码和超时均可由模拟提供者主动抛出，不代表真实网络产生过这些故障：

| 预设序列 | 总尝试上限 | 调用次数 | 等待次数 | 最终结果 |
| --- | --- | --- | --- | --- |
| 401 → 成功 | 3 | 1 | 0 | 抛出 401 |
| 503 → 成功 | 3 | 2 | 1 | 返回成功结果 |
| 503 → 503 → 503 → 成功 | 3 | 3 | 2 | 抛出最后的 503 |
| `ValueError` → 成功 | 3 | 1 | 0 | 传播 `ValueError` |
| `TimeoutError` → 成功 | 3 | 2 | 1 | 返回成功结果 |
| 503 → 400 → 成功 | 3 | 2 | 1 | 抛出 400 |
| 503 → 503 → 成功 | 2 | 2 | 1 | 抛出第二个 503 |
| 任意序列 | 0 | 0 | 0 | 拒绝非法上限 |
| 503 → 成功 | 1 | 1 | 0 | 抛出首个 503 |

下面是基于上述实现补充的最小验证例子：

```python
events = iter([503, 400, "成功"])
calls = []
waits = []


def fake_provider():
    event = next(events)
    calls.append(event)
    if isinstance(event, int):
        raise HTTPError("https://example.invalid", event, "模拟失败", None, None)
    return event


from unittest.mock import patch

with patch.object(time, "sleep", side_effect=waits.append):
    try:
        call_with_retry(fake_provider)
    except HTTPError as error:
        assert error.code == 400
    else:
        raise AssertionError("应传播第二次调用的 400")

assert calls == [503, 400]
assert waits == [0.1]
```

`patch` 临时替换等待函数，记录安排的等待时间，不真正休眠；退出 `with` 后恢复。此例只验证分支、次数和等待安排，不证明真实等待时长或网络故障覆盖。成功场景还应检查返回结果；持续失败场景应检查最后异常，而不只检查“没有无限循环”。
